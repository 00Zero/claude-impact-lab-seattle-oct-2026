  AgenticLantern

  What it does: It helps a family after someone dies. A case gets started, and
  an AI agent recommends funeral homes that fit the family's needs.

  Two ways in, one shared pipeline

  1. Hospital flow: Hospital staff log into a portal and fill in an intake form
     for the patient who died. They enter a family contact's email or phone. The
     system creates a Case and a one-time InviteToken, then sends the family a
     link at /invite/{token}. The family signs up through that link and sees the
     hospital's details already filled in. They confirm or correct them, and
     they don't have to re-type anything.
  2. Self-serve flow: The family signs up directly with no token and fills in
     the same intake form themselves.

  Both paths create the same Case record and lead to the same recommendation
  step.

  Main data records

  - Case: details about the person who died, burial or cremation, any prepaid
    funeral plan, religious or cultural needs (Hindu, Muslim, Jewish, Christian,
    secular, other), location (zip or county), budget, family contact, source
    (hospital/self_serve) and status (awaiting_family → active →
    recommendations_ready).
  - HospitalAccount and FamilyUser: one family user per case, a simplification
    for the hackathon.
  - InviteToken: decides which case a new family user is linked to. It is not
    used for login itself.
  - FuneralHome: a seed list of 10–20 Washington-state funeral homes stored as
    JSON or CSV. It covers what each home can do, cultural tags, prices from
    their published price lists, and ratings.
  - Recommendation: a ranked shortlist with a one-line reason for each home,
    e.g. "handles Hindu cremation, 12 min away, from $X".

  How the AI agent works

  It filters the funeral homes by location, burial or cremation capability, and
  religious tags in code. Then it makes one Claude call that takes the case
  details and the filtered homes and returns a ranked list with a reason for
  each. There is no multi-agent setup in this milestone.

  Suggested tech stack

  Next.js for the frontend and API routes, Supabase (Postgres plus Auth with a
  hospital | family role), and Claude for ranking.

  What "done" looks like (demo)

  1. The hospital creates a case.
  2. The invite link is generated. Showing it on screen is fine.
  3. The family signs up through the link and confirms the pre-filled details.
  4. The family sees 3–5 ranked funeral homes.
  5. The self-serve path is demoed separately.

  Out of scope for now

  - Real hospital integration or single sign-on
  - Live scraping of funeral home price lists or calling funeral homes
  - Multi-agent features (vetting, negotiation, post-funeral checklists)
  - Multiple family members per case
  - Payments or document generation
  - General reading of uploaded PDFs (OCR)

  The spec says this repo is a cut-down version of a bigger system called
  "Ntrust," which has those voice and price-scraping agents.

  Open questions in the spec

  - Cause of death: whether to collect it at all. It's sensitive, and the spec
    leans toward leaving it out.
  - Sending invites: really sending email or SMS (e.g. Resend or Twilio), or
    just showing the link on screen.
  - Family login: a password, or magic-link only.

⏺ I re-read docs/spec.md. It's tightened up a lot since the last version (PDF
  parsing with confidence scores, magic-link auth, resolved questions section) —
  good progress. Here's where it still has real gaps or outright
  inconsistencies.

  Bugs / inconsistencies (fix regardless of product direction)

  1. awaiting_family is a dead status. The Case.status enum is awaiting_family |
     pending_review | active | recommendations_ready, but the hospital flow now
     sets status to pending_review right after upload — nothing ever sets
     awaiting_family. It's a leftover from the pre-PDF version of the spec. Drop
     it from the enum.
  2. The "Resolved questions" section contradicts itself on email. It says email
     is a required field "everywhere a family contact is captured (hospital
     upload form and self-serve signup)," then two lines earlier describes a
     fallback for "a hospital that truly only has a phone number" — but if email
     is required on the form, that hospital can't even submit the case. Pick
     one: either (a) email stays required and you drop the phone-only fallback
     as a real scenario, or (b) phone becomes an alternate required-one-of field
     and the invite flow has an SMS-or-manual path for phone-only cases. (b) is
     more realistic for how hospitals actually work, but (a) is far less to
     build. I'd keep (a) for Milestone 1 and just delete the contradictory
     fallback sentence.
  3. Wizard question count mismatch. Section 3 lists 5 wizard questions
     (location, disposition, religious/cultural, budget, email). The demo script
     (step 6) calls it "the 4-question wizard." Pick the real number and make
     both match.

  Gaps that need a concrete decision

  4. Invite token identity isn't verified. Anyone who gets the /invite/{token}
     URL — forwarded in a group text, read off a shared screen — can sign in
     with any email and get permanently attached to that Case; nothing checks
     the signer against the family contact email the hospital entered. Given the
     Case contains decedent info, this is worth closing even for a hackathon:
     lock the magic-link email field to the hospital-entered contact email
     (prefilled, non-editable) so the token only ever attaches the intended
     person.
  5. No fallback when the recommendation filter returns zero funeral homes. The
     agent step is a hard filter (location + disposition + religious tags) then
     an LLM ranks the survivors. With only 10–20 seeded homes, it's easy for a
     demo county + religion combo to filter to empty — which means the
     recommendation screen can go blank live in front of judges. Define a
     fallback ladder up front: drop religious filter → widen location → drop
     disposition filter → always show something, with the rationale saying
     plainly "closest matches; exact requirements not fully available in our
     area."
  6. Free-text religious/cultural answers never reach the filter. The pre-filter
     matches on structured tags only. If someone picks "other" and types
     "Sikh," that information only reaches the LLM at the ranking step — after
     the candidate set has already been narrowed by tags that don't account for
     it. Concretely: when the requirement is "other" + free text, skip the
     religious tag filter entirely (location + disposition only) and let the
     ranking LLM call do the semantic matching and write the rationale.
  7. No PDF failure path. What happens on a corrupted file, a scanned/non-text
     PDF (explicitly out of scope for parsing, but someone will upload one), a
     PDF unrelated to a death, or a parse that returns nothing usable? Right now
     "low-confidence fields are left blank" covers partial failure but not
     total failure. Add: client-side validation (must be application/pdf, size
     cap, e.g. 10MB) plus a defined "parse produced nothing" case state that
     still creates the Case/InviteToken with blank fields and flags it to
     hospital staff, rather than failing silently or crashing the upload.
  8. "A few GPL price points" is too vague to build from. You need a fixed,
     consistent set across every seeded funeral home or the rationale text
     ("cremation from $X") won't mean the same thing home to home. Pin it to 2–3
     concrete FTC-style categories — e.g. direct cremation, immediate burial,
     traditional full-service package — and require every seed row to have all
     of them.
  9. Budget range has no defined input shape. Free numeric range vs. fixed
     buckets changes both the UI and the matching logic. Recommend fixed buckets
     (e.g. <$3k, $3–6k, $6–10k, $10k+, "not sure") — faster to build, maps
     cleanly onto the GPL price points above, and is a gentler UI for someone
     doing this right after a death.
  10. Invite token lifetime is still unresolved. It says "one-time (or
      short-expiry)" — that's not a decision, that's the open question restated.
      Pick: one-time use + fixed expiry (e.g. 7 days), and add a "resend
      invite" action on the hospital dashboard (mints a new token, invalidates
      the old). A grieving family member not clicking a link within a day or two
      is the realistic case, not the exception, and there's currently no
      recovery path at all if it expires or gets lost.

  Smaller things worth one line each

  - Hospital dashboard is implied, not specified. "Hospital logs in, selects
    'New case'" implies a list view of existing cases, but there's no entity or
    flow for it — what statuses/fields the hospital can see per case (parsed
    data? confidence? whether family signed up yet?) isn't written down
    anywhere, so it'll get improvised during the build. Worth a short paragraph.
  - No access-control statement. Given the Case contains decedent + family PII,
    one sentence on who can read a Case (assigned hospital account + linked
    FamilyUser only; PDFs in a private, non-public storage bucket) is cheap
    insurance, especially if this gets shown to anyone outside your team.
  - No demo-day LLM robustness note. Two separate live Claude calls (PDF parse,
    ranking) with no stated timeout/retry behavior. A single slow/failed call
    during the actual demo is a real risk — worth a one-time retry and/or a
    canned fallback result tied to the sample PDF specifically for the live
    demo.
  - Duplicate-Case edge case isn't addressed. Same family email could self-serve
    a Case, then later get hospital-invited for the same death into a second,
    disconnected Case. Not worth solving for M1, but should be an explicit
    bullet under "Explicitly out of scope" rather than just unmentioned.

  What maps cleanly to Azure:
  - Hosting the Next.js app → Azure App Service (Linux/Node) or Azure Container
    Apps. Straightforward either way.
  - Postgres → Azure Database for PostgreSQL – Flexible Server. Direct swap for
    Supabase's DB, no issue.
  - PDF storage → Azure Blob Storage, private container + SAS tokens for scoped
    read access. Direct swap for Supabase Storage.

  What doesn't map cleanly:
  - Magic-link auth — this is the one place Supabase was doing real work for us

    auth service for this pattern. Azure AD B2C exists but is enterprise
    SSO-shaped and overkill/slow to configure for a one-time family magic link.
    The realistic Azure-native path is Auth.js (NextAuth) with its Email 
    provider, backed by a sessions table in the same Postgres DB — it does give
    you magic links, but it's now something we build and wire up ourselves
    instead of getting for free.

⏺ React instead of Next.js — yes, and it fits well. A plain React app (Vite +
  React, not Next.js) separates cleanly into:
  - Frontend: a static React build — hosted on Azure Static Web Apps, which has
    a generous free tier and pairs natively with Azure's managed Functions for
    an API, without needing a Node server running 24/7.
  - Backend: you actually need very little custom backend. Supabase's JS client
    can call Auth (send/verify the magic link) and do DB reads/writes directly
    from the React app with Row-Level Security — no custom auth or CRUD backend
    required. The only things that must run server-side are the two Claude calls
    (PDF parse, ranking), since the Anthropic API key can't live in client
    code. Those become two small Azure Functions endpoints.

  So with React, the natural Azure-native shape becomes: Azure Static Web Apps 
  (frontend) + Azure Functions (the two LLM endpoints) + Supabase (Postgres + 
  Auth + PDF storage). That's a smaller build than either of my original options
  — real Azure usage for hosting/compute, Supabase doing the auth/DB/storage
  work it's already good at, and almost no custom backend to write.

  Is Supabase free? Yes, for this scale. The free tier covers a single hackathon
  demo easily — generous DB storage, 1GB file storage, Auth with no practical
  user-count issue at this scale, two free projects. The one gotcha worth
  knowing: a free-tier project auto-pauses after about a week of no activity and
  needs a manual "restore" click in the dashboard before it's usable again — so
  if there's a multi-day gap between finishing the build and the actual demo,
  go poke it awake beforehand rather than finding out live.
